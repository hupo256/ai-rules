## 2. 结论

1. **浏览器验证是最贵也最长的单一阶段**：中到大需求里占 13–52% token，单个浏览器 agent 墙钟 65–152 分钟，是需求墙钟的关键路径（02012 R1 约 2 小时里浏览器占一半以上；02418 三轮 151 分钟）。浏览器 agent 的上下文峰值普遍最高（02306 242K、02022 265K、02265 253K），说明截图与 report 在反复累积。v1.7 的「按站点并行」「prewarm」只能压墙钟，压不了 token。
2. **执行主体/主会话是第二大项**（19–51%）：主会话模式下 34–44%，agent 模式下 24–51%。它做的是读 PRD、建清单、批次 0、合并 diff、修复、交付说明。小需求（01723）几乎全在这里，说明「主会话直写」的下限约 40–50M。
3. **冷读稳定在 9–18%**，R1 20–50M，R2 约为 R1 的 1/3–1/2。不是优化重点。
4. **编码随并行子 agent 数线性增长**：每个编码 agent 7–26M；02374 七个 96M。并行省的是墙钟不是 token。
5. **读图 + 落点 ≤ 12%**，可忽略。
