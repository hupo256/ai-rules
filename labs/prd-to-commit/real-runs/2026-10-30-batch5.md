## 2. 关键发现

1. **候选筛选错误（编排方）**：「远端分支领先 online 0 个提交」被误读为「空分支」，实际是**已合入 online**。PR-02127、PR-02254 因此变成「在已有实现上按 PRD 复核补缺」，数据不能与从零实现混算。正确判据：分支提交是否为 base 祖先（`git merge-base --is-ancestor`）+ base 历史里是否已有该需求提交。
2. **「补缺口」模式本身有价值**：两个需求都找出了首轮实现与 PRD 的偏差（PR-02127 被删掉的「当日跟单者总数」列、实际分润被截成非负；PR-02254 非发起人按钮 disabled 导致提示永不出现、平台页默认时间越界改动等），且改动很小——等同于「PRD 准出复核」。skill 未覆盖这种模式。
3. **React 19 运行时不兼容第 2 次**：PR-02254 antd 静态 `message` 不渲染（PR-02374 是 react-quill 白屏）。tsc/冷读都看不出，只有浏览器能发现。
4. **浏览器验证仍是最长环节**：PR-02012 浏览器 R1 约 2h（4 站点串行、legacy 首次 npm install）；PR-01549 浏览器 3 轮 + 续跑。
5. **原型附件**：PR-02634（1 个）、PR-02012（7 个）的 HTML 原型 fetch-prd 未下载，编排方手动补；lark-cli `--output` 只接受相对路径（绝对路径静默失败）。

**核心结论**：
1. **目标工程/应用选择 3/3 与同事不同**——这是本批最大的风险：PRD 正文全覆盖（漏项 0–1），但代码可能落在不上线的工程里。skill 目前在 §2/§4 都没有「目标工程判定」，fameex.md 的 web-next 小节只说「资产页等还在 apps/web」，没有「新页面/活跃模块看近期提交与在途分支」的判据。
2. **PRD 覆盖度已不是短板**：3 个从零需求漏 PRD 项合计 1 项；同事反而漏得更多（14 项，部分联调后主动暂停）。
3. **契约缺失是联调成本的主要来源**：有同类契约时，「镜像但裁剪」让命中率从可达 97% 降到 74%；全新业务（02012）占位几乎全错，协议结构也不同。
4. **隐含需求（App WebView 能力、错误码分支、上限口径含已成交）**是剩余差距，均为 PRD 未写、同事凭业务经验补的。

对照子 agent 给出的 skill 启示（合并去重，落到章节）：
- §2/§4 前置「目标工程判定」：同业务在 web 与 web-next（或独立 app）都有实现时，比较 online 近期提交活跃度、首页入口所在工程、同模块在途分支；判定不了作为**阻塞问题**问，直接做模式也要在交付说明首行标出。（01549、02634、02012）
- §3：PRD 无契约时向用户要 YApi/枚举码；远端已有 `feature/<ID>` 时问是否以其契约层为准（02012）。PRD 写「独立系统」时把「独立应用 vs 内嵌」列为待确认（02012）。
- §2 接口占位：有同类契约时整份照搬全部字段、只换业务段路径；「沿用某接口命名」须逐字段抄全；搜仓内语义相近的真实接口作为候选契约（01549、02634）。
- §2 清单：PRD「通用规则」章节（时间口径、空值、精度）作为全局约束逐页核对；修改类需求核对上限是否含已成交/冻结并代入部分成交数值；错误码做同因搜索按码分支（01549、02634、02012）。
- §2 同因：新增审批来源要同步审批列表业务类型枚举；加列要决定是否进可配置列；替换/删除控件只作用于 PRD 谓词命中的对象（02012）。
- fameex.md：新增 App WebView 小节（原生分享 showShare、返回刷新 pageshow/visibilitychange、客服浮窗隐藏）（02634）。
