| 现象 | 根因 | 先做什么 |
|---|---|---|
| Skill 装了却不触发 | 发现、路由、执行三层有一层没通 | 先显式调用，再查 description 和路径 |
| 全局和项目 Skill 打架 | 同名 Skill 有两份来源 | 只保留一个权威来源 |
| 规则写了但 Claude 不听 | 四层提示词职责混在一起 | 把事实、流程、全局约束拆开 |
| 追加 system prompt 后行为变怪 | 替换/追加、全局/临时混用 | 先 `--help` 核对参数，再只加边界 |
| MCP 注册了却不用 | 工具能启动 ≠ Agent 会选择 | 查启动、描述、任务路由三层 |
| 同一套 Skill 换 Agent 失效 | 核心流程和宿主配置绑死 | 拆核心层和适配层 |

## 逐节要点

### 1. Skill 不触发：三层链路
- 发现（当前会话的 Skill 搜索范围看不看得到）→ 路由（description 有没有说清「什么时候用我」）→ 执行（Skill 里的路径、命令、工具在当前环境真的存在）。多数人只查了第一层。
- 最小可路由的 SKILL.md：description 写触发场景、任务边界、**不适用场景**（例：`Use when reviewing a backend service change, especially when the task touches database writes, retries, permissions, or idempotency. Do not use for simple formatting changes.`）。
- 排障顺序：显式调用一次确认本体能跑 → 看 description 是否具体 → 最后才怀疑模型。显式调用也失败 = 路径/执行层问题，不是路由。
- 反例：description 写成宣传词 + 正文 500 行流程。

### 2. 全局 vs 项目：唯一真源
| 类型 | 位置 | 内容 |
|---|---|---|
| 个人习惯 | 用户级目录 | 审查清单、提交习惯 |
| 项目规则 | 项目级目录 | 测试命令、模块边界、发布流程 |
| 团队能力 | 团队仓库 / 固定 plugin（有版本） | 共享审查流程、安全约束 |
- 最危险：同名 Skill 同时在用户级、项目级、plugin 三处，改的和读到的不是同一份。
- skills.sh（可编辑副本）与 plugin（只读订阅）二选一作权威来源，另一个只做临时试验、试完删。
- 别把所有 Skill 塞全局：项目 A 的工作流会带进项目 B。

### 3. 四层分工（图 1「Claude Code 上下文分层」）
- system prompt = 驾驶规则（怎么用工具、怎么拆任务、何时停下确认）；CLAUDE.md = 入职手册（技术栈、测试命令、模块边界、禁区）；Skill = 操作手册（某类任务的检查→修改→验证顺序）；当前对话 = 本轮边界（文件范围、输出格式、确认条件）。
- 判断标准：**这句话复制到另一个项目还成立吗**——成立放全局；不成立放项目；只有做某类任务才需要放 Skill；只对本轮有效写进当前对话。
- 两种坏结果：项目事实污染全局（换仓库还带旧表名）；工作流写进 CLAUDE.md（每次对话都加载，偶尔才用，白占 Token 和注意力）。
- 「规则不是越集中越好，职责清楚才是省 Token。」

### 4. `--append-system-prompt` 不是万能增强包
- 适合：本轮稳定的全局边界（只许改 `src/`、禁止发布命令、删除前确认）。不适合替代项目文档、Skill、测试。
- 坑 1：`--system-prompt` 是**替换**默认系统提示词，`--append-system-prompt` 是**追加**；想补一条边界却把工具使用策略整个覆盖，模型「变笨」其实是方向盘被拆了。
- 坑 2：互相冲突的约束一起塞（先规划再改 vs 立即改；任何命令都确认 vs 完全无人值守）→ 模型随机取舍。
- 只追加三类：安全边界、本会话权限范围、必须遵守的输出格式。命令：`claude --help | grep -E -- '--(append-)?system-prompt'`、`claude --append-system-prompt "$(cat .claude/guardrails.md)"`。

### 5. MCP 注册了不用（图 2「MCP 不调用的四步排障」）
- 四步：注册检查（配置文件在、CLI 能列出）→ 进程启动（路径/运行时/环境变量）→ 描述清楚（什么时候用、返回后如何验证）→ 任务路由（任务给出调用理由；先查图谱再回源）。每步失败回查对应层，不要先重装。
- 命令：`claude mcp list`、`cat .mcp.json`、`command -v node`、`node --version`。
- tool description 要写「什么时候用」而非「我能做什么」，且写明「返回后仍需打开源文件和测试确认」——MCP 返回的是证据线索，不是最终答案。
- 反例：接 20 个 MCP 指望它像架构师一样选。先接少量高价值工具，写清描述和回归场景。

### 6. 一套 Skill 多 Agent 复用：核心层 + 适配层
| 内容 | 可复用 | 处理 |
|---|---|---|
| 检查清单、领域术语 | 高 | 放核心 Skill |
| 文件路径、命令 | 中 | 按项目改写 |
| MCP 工具名 | 低 | 每宿主单独适配 |
| 权限与确认机制 | 低 | 不要直接复制 |
| 结果格式 | 中 | 先统一再按宿主调 |
- 核心层只写任务方法（收集什么、按哪些风险检查、什么算完成）；适配层各几十行写宿主的工具名、配置目录、调用方式。迁移的是能力边界，不是目录结构。

### 7. 代码图谱是导航，不是目的地
- 三条规矩：先查更新时间与当前分支；图谱只缩小范围，命中文件必须回源读；写操作/迁移/权限改动至少再看测试与调用方。
- 数据：sense 工具调用 19→10 次、Token 228K→156K——省下的调用拿去验证，不是省略验证。小仓库别为热点上图谱；值得接的是跨模块调用多、同名符号多、Agent 反复翻源码的仓库。

### 8. PDF 检索省 Token 却答错图表
| 问题类型 | 路径 |
|---|---|
| 条款、定义、章节、关键词 | 本地 RAG |
| 表格数字 | 先文本检索，再核对原页 |
| 架构图、流程图、扫描件 | 原生多模态 |
| 既问正文又问图表 | 两路合并 |
- 「92%→99% 节省」是特定文档特定基准线的结果。省 Token 的前提是没省掉答案需要的证据。

### 附：只读体检脚本（原文 `scripts/claude-code-doctor.sh`）
检查 `~/.claude/skills`、`./.claude/skills` 下的 SKILL.md；`~/.claude.json`、`./.mcp.json`、`./.claude/settings.json` 是否存在；`claude --version`、`claude mcp list`。只筛「目录不在、配置不在、CLI 不在 PATH、MCP 列表为空」这类低级问题；脚本正常而 Agent 仍不触发时，回到任务描述和 tool description 查路由。

### 常见问题（原文 Q&A）
- Skill 不是越多越好：价值是减少重复决策；先留能明确说出触发条件、输入、验收方式的少数几个。
- Skill 写了「必须调用 MCP」仍不用：「必须」不是路由证据，要把时机、能解决什么、调用后怎么验证写进 tool description，并在任务里点名第一步。
- 代码图谱不能替代 CLAUDE.md：一个答结构关系，一个答项目约定。
- 不是所有 PDF 都该接 Token Saver：图表密集、扫描件、要保留版式的先用多模态。
- 不只 Claude Code 能用这些 Skill：核心流程可复用，配置路径、工具名、权限机制要适配。
