# PRD → Commit

目标：第一次就把需求做全，过程尽量短。**不写阶段报告、不跑门禁引擎、不建项目文档目录。**产物只有代码提交、清单、plan 和 run-log。

脚本目录：`~/.ai-rules/skills/prd-to-commit/scripts/`（下称 `$S`）。

## 1. 拉 PRD（只一次）

```bash
node $S/fetch-prd.mjs <ID> <lark-url>          # → ~/.prd-cache/<ID>/r<rev>/{prd.md,prd.xml,media/,sheets/,meta.json}
```

- 完整读 `prd.md`，**逐张看 `media/` 里的图**（图里常有页面、文案、红框标注）。之后只在疑点处回查本地文件，不重拉。
- 内嵌表格会自动导出到 `sheets/`，并在 prd.md 里原位展开成 csv 块，要和正文一起读完。`meta.json.unexpanded` 列出的多维表格、iframe 等需要人工查看。
- `meta.json.failed` 非空或有 Figma/原型链接读不到：告诉用户缺什么，然后继续其余部分。
- 用户另外给的输入（接口契约、YApi 导出、附件、Figma 链接）存到 `~/.prd-cache/<ID>/inputs/`，清单、编码和冷读都要引用。
- 用户直接贴正文时，把正文存为 `~/.prd-cache/<ID>/manual/prd.md`。

## 2. 需求清单 `~/.prd-cache/<ID>/checklist.md`

清单是整个流程的核心。漏需求几乎都漏在「条目 → 具体页面/文件」这一步，所以每条都必须落到具体位置：

```markdown
| # | PRD 原句（逐字，附章节/图号） | 端 | 页面/入口（全部列出） | 落点文件（找代码后填） | 文案（逐字，未指定写「未指定」） |
```

规则：
- 核对后现状已满足、无需改代码的行，落点写「已兼容：<文件:行> + 一句理由」；冷读对这类行只核实证据是否成立。
- **一个页面一行**。「登录/注册/找回/重置都要…」就拆成 4 行，不许合并成一行。
- 端：`web` / `admin` / `futures-admin` / `非前端`（非前端只留一行说明，不展开）。用户指定只做某端时，其余端标「不做」并注明。
- 删除线、「本期不做」只按 PRD 原文判断，不要自行推断。拿不准的，标 `?` 放进待确认。
- 依赖后端的字段：写出接口名或字段名；未知就写「待确认」，**不要编造字段**。后端口径不明的地方列进待确认。
- 需要某个口径值（如「只含普通体验金的可用额」）时，**先在 schema/类型定义里搜现成字段**（常见命名如 `normalXxx`、`xxxExclude`、`availableXxx`），有就直接用；没有才列待确认。不得用合并值减去分项、逐条求和等兄弟字段算术去推算（全局规则），即使标了待确认也不行。PRD 明文给出的计算公式（如「使用中 = 冻结 + 占用」）照公式实现，不算反推。
- 字符串取值的渠道名/类型名（如 `Telegram`、`Facebook`）如果仓内同类值已有固定写法且被严格解析，沿用该写法并列待确认，不用非法占位（否则解析整体失败）。
- 仓内已有**语义完全相同**的错误码/枚举（PRD 也写明沿用现有逻辑）时，直接复用并列待确认，不另设占位（否则对应分支永远不触发）。
- 枚举码、流水类型码这类值不能按约定去猜：列进待确认，在 §3 问用户要。回放模式或用户暂时给不出时，落点代码照样写好，值用明显非法的占位（如 `'-1'`，不要按现有码顺延去猜），加上 `TODO(<ID>): 待后端确认`。占位常量集中定义在一个文件里，其他地方引用它，并在交付说明里列出。**多值枚举（状态、类型）的每个值各用一个互不相同的占位**（如 `'-1'`/`'-2'`/`'-3'`），不能共用一个值，否则分支逻辑区分不开。接口路径/字段完全未知时同理：集中写在一个 service 文件里，逐项标 TODO，业务逻辑照 PRD 写全。不能因为缺码就让这个端零改动。
- PRD 文字和原型图冲突时，以文字为准，并把冲突列进待确认。PRD 内部自相矛盾时（如产品方案章节 vs 验收用例/存量处理/附录），**以产品方案正文（含其删除线）为准实现**（正文各小节之间也不一致时，各小节按各自正文），矛盾列进待确认；不要因为矛盾就退回现状不改。
- 页面上的规则提示/勾选清单必须与实际提交校验一致：不能出现「提示全部通过、提交却被拒」。PRD 文案少写了某个校验条件时，列进待确认，并让显示与校验保持一致（把该条件并入已有提示项或补一行），不要只改显示或只改校验。用新提示替换旧提示时，旧提示写明的条件（如「含数字」）新提示里也要能看到。
- 收紧或改变校验规则（密码、格式、长度等）时，把用到它的入口分成两类：**设置新值**（注册、修改、重置）套新规则；**验证已有值**（登录、校验旧密码、二次验证）保持宽松或只做非空，否则存量用户会被锁在门外。拿不准的列进待确认。
- 后台**新增页面**放在同一菜单分组的兄弟页面所在的工程（先找兄弟页面的路由文件），注册点（路由、菜单配置、权限）照兄弟页面一样登记。不要 legacy 和 Next 两套都做，也不要篡改后端菜单接口的返回数据。只有兄弟页面本身分布在两个工程时，才列进待确认。
- 找落点时，「后台/管理端」的页面要连 Vue2 旧工程一起搜（FameEX：`apps/admin/legacy-admin`、`apps/futures-admin/legacy-admin`）。只有搜过这些目录仍找不到，才能写「本仓无此页面」，并附上用过的搜索词。
- 先用 Grep/Glob 找代码再填落点。落点多、分散在不同 app 时，可以开多个 Explore 子 agent 并行找。每条都要做一次**同因搜索**：同一常量、正则、枚举、组件、文案 key 在仓内的所有拷贝和调用入口（包括写死的字面量副本）。i18n key 两种写法都要搜：扁平的 `"a.b"` 和嵌套的 `"a": { "b" }`。
- 语言文件按仓库规则处理（FameEX Web：`AGENTS.md` 规定只改 zh-CN）。其他语言不同步时，在清单里注明依据。
- FameEX 仓库的已知坑（i18n 命名空间登记、MSW 放行、登录态验证等）见 `references/fameex.md`，碰到相关改动时再读。

## 3. 用户确认（一次）

给用户看清单、「待确认」列表和 §3.5 的计划，**问完就停下等回复**。用户说「直接做」或者在回放模式下，跳过这一步（计划照写）。确认后不再中途打扰、不逐步汇报，一直做到 §9；遇到真正阻塞（权限、账号、接口完全缺失）时，再问一次具体问题，并继续做不受影响的部分。

## 3.5 计划与并行批次 `~/.prd-cache/<ID>/plan.md`

把清单行归并成步骤，每步写：覆盖的清单行、要改/新建的文件、依赖哪些步骤。按依赖分批，每批标明是否派子 agent 及理由：

- **批次 0（主会话串行）**：先定下所有步骤都要用的契约，包括类型/schema、service 接口、路由与路径常量、i18n 文件和 key 骨架、共享组件的 props。只有后面还要派并行子 agent 时，批次 0 写完才先跑一次 check.mjs 锁定契约；串行时直接放到 §6 一起查。不依赖契约的步骤（例如在现有枚举、文案里加项）不用等，和批次 0 同时开工。
- **能否并行看依赖**：两批互不改同一文件、只依赖批次 0 已定的契约、不需要对方的产出，才算可并行；否则排成先后批次。
- **值不值得派看工作量**：可并行的批次里，只派工作量明显大于子 agent 重建上下文成本的（如另一个工程、独立页面）；零散小改动（加枚举项、文案 key）主会话顺手写，派出去回放实测 token 翻倍、墙钟不降。没有值得派的就全程串行。
- **值得派的有 ≥2 批时**，主会话只做批次 0、合并和验证，不写大段 UI（主会话上下文越长每轮越贵）；只有 1 批时派它出去，主会话写主线。
- **派子 agent 时**：每步一个子 agent，给它负责的清单行原文、可写文件清单（越界只读）、契约文件路径、§5 编码规则。要求它不跑 git、不跑全量检查，做完返回改了哪些文件、还有哪些未决问题。主会话等这一批都返回后，**逐个看 diff 合并**，不要只看子 agent 的报告，报告和实际改动可能不一致。合并好再开下一批。如果需要改共享组件，要在派活时写明只允许做什么（例如「只加可选 prop」）。
- Explore 子 agent 同理：落点跨 ≥3 个工程时才并行开多个，否则主会话直接搜。
- 冷读默认在前台运行并等待结果（§6 静态检查通过后立即开始）。只有主会话确有不改代码的事要并行做（如浏览器核对）、且确定能收到后台通知时才放后台。**冷读结果回来之前不能进入 §8/§9，也不能结束或交回任务**。

在 `~/.prd-cache/<ID>/run-log.md` 记下每批的起止时间、返工原因和意外，供事后复盘。

## 4. Worktree

```bash
node $S/worktree.mjs <ID> [--fix]              # → ~/github/<ID>，feature/<ID> 基于 origin/online，自动装依赖
```

已存在就复用。远端已有同名分支时脚本会拒绝创建：改用 `--branch <名字>`，或者问用户是否在远端分支上继续。之后所有改动都在该路径内进行。

**禁止在 fameex-web 用 `git stash`**：所有 worktree 共用一个 stash 栈，pop 可能弹出别人的改动。需要对比改动前后时，用 `git show HEAD:<file>` 或临时 worktree。

## 5. 编码

- 按 §3.5 的批次推进：批次 0 主会话自己写；后续批次按 §3.5 判定值得派的才派子 agent，其余主会话串行写，派出时主会话负责合并和对齐契约。
- 遵守全局规则和仓库 `AGENTS.md`/`CLAUDE.md`、按主题命中的 `.cursor/rules/*.mdc`、`coding-quality` skill。不需要额外读其他东西。
- 按清单逐行实现。实现完一行，就在清单「落点文件」列填上真实路径。
- 文案按 PRD 逐字写入，语言文件范围按仓库规则。文案里含 `&`、`/`、`<` 等符号且走 i18next 插值时，要防止被转义成 `&amp;`；能直接写进文案就不要用插值。
- 接口未就绪（dev 上还没有或字段不全）时，按已知契约写好代码，在清单里标「待联调」，并**自行决定**加最小 MSW mock 把 UI/UX 写全、本地能点通，不用等用户提出：只为本需求新增/变更的接口写 handler 和 fixture，放 `src/mocks/<功能>/`，只在 `NEXT_PUBLIC_ENABLE_MSW=true` 的本地开发下生效，业务代码里不写 mock 分支。该 app 还没有 MSW 接入时，按 `references/fameex.md` 的清单单独一个提交补齐；legacy Vue2 工程不接 MSW。接口上了 dev 就删对应 handler 和登记行、改走真实请求，MSW 基建保留不删。只为验证构造的边缘数据态（空、报错、极端值）写在浏览器验证 spec 里，不进 MSW。
- 写操作（绑定/解绑/提交/删除/状态上报）成功后，要让依赖该数据的服务端状态刷新（React Query `invalidateQueries` 用户资料、列表等），不能只关弹窗、弹提示。

## 6. 检查（只查改动）

```bash
cd ~/github/<ID> && node $S/check.mjs [--base <BASE>]   # biome + tsc（只报改动行）+ code-rules（豁免写 `// code-rules-ignore <ID>: <理由>`）；legacy JS/.vue 做语法检查；改动的测试文件跑 vitest
```

手动跑格式化（`biome check --write` 等）时只传本次改动的具体文件，不要传目录，否则会格式化无关文件。输出里的 `not-covered`（例如 legacy `.vue` 模板）不能算通过，要在交付说明里如实写出。

**浏览器验证（改动涉及可见 UI 时必做）**：按 `references/browser.md` 用 `dev.mjs` 起固定端口的 dev server、`browser.mjs` 复用已保存的登录态跑验证 spec（接口没好就在 spec 里 mock；dev 上写操作默认真实执行，其他环境一律拦截），逐张查看截图对照 PRD/Figma。登录态失效时请用户执行 `browser.mjs login --site <site>`，期间先做其他验证；确实跑不了的写 `not-covered: <原因>`，不要假装通过。

## 7. 独立冷读（必须用子 agent，不能自查）

开一个**全新上下文**的子 agent（Claude 用 Agent 工具；Codex 用新会话或子代理）。只给它下面这段话，不要附带你的推理过程：

`<BASE>` 默认取 `git merge-base HEAD origin/online` 的结果；回放时用指定的 base commit。冷读前先 `git -C ~/github/<ID> add -N .`，否则 diff 里看不到新建的文件。

> 你是需求验收员。PRD 在 `<prd.md 路径>`（内嵌表格已展开），图片在 `<media 路径>`，额外输入在 `<inputs 路径，没有就删掉这句>`，代码改动用 `git -C ~/github/<ID> diff <BASE>` 查看。语言文件范围以仓库 `AGENTS.md` 为准。
> 1. 独立通读 PRD 和每张图，列出所有前端可见行为：页面、入口、文案、校验、状态、权限、埋点、多语言。不要看任何现成清单。
> 2. 对每一条，在 diff 中找到实现它的具体位置（文件:行）。找不到就标 **MISSING**。如果交付方声称「本仓无此页面」，自己在全仓搜一遍（包括 `legacy-admin` 等 Vue2 旧工程），找到了就标 **MISSING** 并给出路径。
> 3. 对每个被改的常量、正则、枚举、组件、文案 key，在仓内全局搜索其他拷贝和调用入口（包括写死的字面量副本；i18n key 要搜扁平和嵌套两种写法），把没跟着改的标 **SIBLING-MISSED**。
> 4. 标出与 PRD 原文不一致的文案、校验和行为（**MISMATCH**）。
> 5. 如果改动收紧了校验规则，检查有没有误套到「验证已有值」的入口（登录、校验旧密码等），有就标 **MISMATCH**。
> 6. 检查页面规则提示/勾选状态是否与提交校验一致（有没有「全部显示通过但提交被拒」的输入），以及旧提示写明的条件有没有在新提示里丢掉，不一致标 **MISMATCH**。
> 7. 检查每个写操作成功后，依赖该数据的列表/资料是否会刷新，不刷新标 **MISSING**。
> 被 lint-staged/biome 强制要求的存量最小修复（如去掉 `any`、格式化）不算越界，不用报。
> 只输出问题列表，每条附 PRD 原句和证据。不要修改代码。
> 后端直出的字段/口径不要求前端改写或推算；前端用兄弟字段做算术反推的，标 **MISMATCH**。
> `<额外约束：范围限定、回放的公平性约束等，没有就删掉这一行>`

## 8. 修复（最多 2 轮）

逐条处理 MISSING/SIBLING-MISSED/MISMATCH：修复，或者给出理由（如属后端原因、PRD 明确不做）。**PRD 正文明确要求的改动，不因冷读的顾虑撤回或降级为 blocker**：实现保留，顾虑列待确认；只有确实缺数据、且 schema 里也没有现成字段时，才列为 blocker。冷读指出「改动波及需求范围外的已有行为」（例如共享逻辑改了别的渠道/类型的现有提示）时，默认收窄回需求范围；只有 PRD 明确要求统一时才保留。区分两者：**同因** = 本需求涉及的同一业务对象/字段在其他页面、入口、拷贝里的呈现，必须一起改；**范围外** = 本需求没涉及的其他对象/渠道/类型的已有行为被连带改变，要收窄。同因扩展如果找不到口径依据（如同名字段在不同接口里正负含义不同），不做，列待确认。第 2 轮报出的小问题，证据具体的可由主会话直接修，不必再开第 3 轮。修完重跑 §6 检查。**第 1 轮修过 MISSING/SIBLING-MISSED，或者修复改了 3 个以上文件**，才冷读第 2 轮；否则由主会话逐条核对修复，跳过第 2 轮，并在 run-log 里记一笔。第 2 轮的冷读提示末尾加上第 1 轮的问题列表和处理结论，要求它只复核修复是否到位、新增 diff 有没有新问题、被判「保留」的理由是否成立，不重复报已处理的项。第 2 轮后仍有问题，就把问题清单交给用户，不再空转。

## 9. 提交

```bash
cd ~/github/<ID> && git add -- <本次改动的具体文件...> && git commit -m "feat(<ID>): <一句话>"   # 文件多时：把路径写进文件后 git add --pathspec-from-file=<file>
```

- 只 `git add` 具体文件，不用 `git add -A`。不 push。
- 被 hook 拦下就修代码，不用 `--no-verify`。
- 沙箱里 `.git` 只读、提交失败时（Codex CLI 常见）：`git bundle create /tmp/<ID>.bundle <base>..HEAD` 打包提交（可先在临时 `GIT_DIR` 里提交），并在交付说明里写明 SHA 和 bundle 路径，由用户 fetch 回来。

## 10. 交付说明（给用户，≤15 行）

包括：提交 SHA；**上线前必须替换的占位**（码值、接口路径、配置 ID，逐个列文件:行，并注明占位选项现在是否会被用户选到）；清单完成情况（✅ / 待联调 / 待确认）；MSW mock（handler 文件与对应接口，接口上 dev 后删除）；冷读发现了什么、怎么处理的；哪些检查跑了、哪些没跑（直接写 `not-required` 或原因）。

交付前运行 `node $S/stats.mjs <ID>`，把 token 和墙钟追加到 run-log，并在交付说明末尾附上一行合计。
