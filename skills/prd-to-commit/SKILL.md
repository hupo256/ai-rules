# PRD → Commit

目标：第一次就把需求做全，过程尽量短。**不写阶段报告、不跑门禁引擎、不建项目文档目录。**产物只有代码提交、清单、plan 和 run-log。

脚本目录：`~/.ai-rules/skills/prd-to-commit/scripts/`（下称 `$S`）。

## 1. 拉 PRD（只一次）

```bash
node $S/fetch-prd.mjs <ID> <lark-url>          # → ~/.prd-cache/<ID>/r<rev>/{prd.md,prd.xml,media/,sheets/,meta.json}
```

- 完整读 `prd.md`。图片（`media/`、Figma 预览）超过 5 张时先派 1 个子 agent 逐张转写（否则自己看）到 `~/.prd-cache/<ID>/media-notes.md`：每张写对应 PRD 位置、页面/状态、**全部可见文字逐字**、红框/标注、与正文的冲突。notes 开头先列每图一行摘要。主会话读 notes 建清单；**编码某页面 UI 前必须看对应原图**核对位置、锚点与布局。之后只在疑点处回查本地文件，不重拉。
- 内嵌表格会自动导出到 `sheets/`，并在 prd.md 里原位展开成 csv 块，要和正文一起读完。`meta.json.unexpanded` 列出的多维表格、iframe 等需要人工查看。
- `meta.json.failed` 非空或 Figma/原型读不到：告诉用户缺什么，继续其余部分。
- 用户另给的输入（接口契约、YApi、附件、Figma）存 `~/.prd-cache/<ID>/inputs/`，清单、编码、冷读都要引用。
- 用户直接贴正文时，把正文存为 `~/.prd-cache/<ID>/manual/prd.md`。

## 2. 需求清单 `~/.prd-cache/<ID>/checklist.md`

清单是整个流程的核心。漏需求几乎都漏在「条目 → 具体页面/文件」这一步，所以每条都必须落到具体位置：

```markdown
| # | PRD 原句（逐字，附章节/图号） | 端 | 页面/入口（全部列出） | 落点文件（找代码后填） | 文案（逐字，未指定写「未指定」） |
```

规则：
- 核对后现状已满足、无需改代码的行，落点写「已兼容：<文件:行> + 一句理由」。理由要对照 PRD 的具体要求逐项成立（要读的字段代码确实在读；等式在展示精度下成立，如分项各自取舍后再相加），不能只是「已有类似逻辑」；涉及等式/精度的代入数值算一遍。冷读对这类行按 PRD 原句复核并代入数值。
- **一个页面一行**。「登录/注册/找回/重置都要…」就拆成 4 行，不许合并成一行。
- 端：`web` / `admin` / `futures-admin` / `非前端`（非前端只留一行说明，不展开）。用户指定只做某端时，其余端标「不做」并注明。
- 删除线、「本期不做」只按 PRD 原文判断，不要自行推断。拿不准的，标 `?` 放进待确认。
- 依赖后端的字段：写出接口名或字段名；未知就写「待确认」，**不要编造字段**。后端口径不明的地方列进待确认。
- **列待确认（或称阻塞）不等于不做**：前端能独立做的部分照 PRD/契约最可能的读法实现（契约或接口文档写明的字段直接用；提示/Toast 没给文案就复用仓内同类文案或自拟；严格 enum 会让后端新值整体解析失败的就放宽），待确认只记风险。
- PRD 写明的显隐/出现条件（「有数据才显示」「超过 N 条才出现」）记进清单，按原文完整实现，不能只判一半或无条件渲染。
- 需要某个口径值（如「只含普通体验金的可用额」）时，**先在 schema/类型里搜现成字段**（如 `normalXxx`、`xxxExclude`、`availableXxx`），有就直接用，没有才列待确认；不得用兄弟字段做减法、求和去推算，标了待确认也不行。PRD 明文给的公式（如「使用中 = 冻结 + 占用」）照公式实现。
- 字符串渠道名/类型名（如 `Telegram`）仓内同类值已有固定写法且被严格解析的，沿用该写法并列待确认，不用非法占位（否则解析整体失败）；仓内已有**语义完全相同**的错误码/枚举（PRD 写明沿用现有逻辑）时直接复用，不另设占位。
- 枚举码、流水类型码不能按约定去猜：列待确认，§3 问用户要。给不出时值用明显非法的占位（如 `'-1'`，不按现有码顺延），标 `TODO(<ID>): 待后端确认`，占位集中在一个文件并在交付说明列出。**多值枚举每个值各用不同占位**（`'-1'`/`'-2'`/`'-3'`），否则分支区分不开。PRD 列了展示名（如平台名）时建「码→展示名」映射，不直出。接口路径/字段未知时同理，集中在一个 service 文件逐项标 TODO，业务逻辑照 PRD 写全。
- PRD 文字和原型图冲突时，以文字为准，并把冲突列进待确认；文字没写而原型画了的层级、布局按原型做，不算冲突；但正文已列举某处的按钮/操作时，原型多出的控件（如 ×）算冲突，以正文为准。PRD 内部自相矛盾时（如方案章节 vs 验收用例/附录），**以产品方案正文（含删除线）为准实现**（正文小节之间不一致时各按各的），矛盾列待确认，不因矛盾退回现状。
- 规则提示/勾选清单必须与提交校验一致，不能「提示全部通过、提交却被拒」。PRD 文案少写某个校验条件时列待确认，并让显示与校验一致（并入已有提示项或补一行）。用新提示替换旧提示时，旧提示写明的条件（如「含数字」）新提示里也要能看到。
- 收紧或改变校验规则（密码、格式、长度等）时，把用到它的入口分成两类：**设置新值**（注册、修改、重置）套新规则；**验证已有值**（登录、校验旧密码、二次验证）保持宽松或只做非空，否则存量用户被锁在门外。
- 后台**新增页面**放在同一菜单分组的兄弟页面所在的工程（先找兄弟页面的路由文件），注册点（路由、菜单配置、权限）照兄弟页面一样登记。不要 legacy 和 Next 两套都做，也不要篡改后端菜单接口的返回数据。只有兄弟页面本身分布在两个工程时，才列进待确认。
- 找落点时，「后台/管理端」的页面要连 Vue2 旧工程一起搜（FameEX：`apps/admin/legacy-admin`、`apps/futures-admin/legacy-admin`）。只有搜过这些目录仍找不到，才能写「本仓无此页面」，并附上用过的搜索词。
- 单工程且落点 ≤10 处时主会话直接搜；否则先派 1 个 Explore 子 agent（跨 ≥3 个工程时每工程一个）：给它清单草稿行，要它返回落点地图（文件:行、≤3 行片段、同因拷贝）。据此填落点，之后**只读要改的区段**，不整篇读 >150 行的文件，读过的不重读；多段/多文件**合在一次调用里读**。每条都要做**同因搜索**：同一常量、正则、枚举、组件、文案 key，以及**被删除/替换的展示字段**（如 `tagLabel`），在仓内的所有拷贝、调用入口和渲染点（含写死的字面量副本）。i18n key 扁平与嵌套写法都要搜。
- 语言文件按仓库规则处理（FameEX Web：`AGENTS.md` 规定只改 zh-CN）。其他语言不同步时，在清单里注明依据。
- FameEX 已知坑（i18n 登记、MSW、运行时坑、图标查找等）见 `references/fameex.md`，碰到相关改动时再读。

## 3. 用户确认（一次）

给用户看清单、待确认和 §3.5 的计划，**问完就停下等回复**。用户说「直接做」或回放模式下跳过（计划照写）。确认后不再中途打扰，一直做到 §9；真正阻塞（权限、账号、接口完全缺失）时再问一次具体问题，并继续做不受影响的部分。

## 3.5 计划与并行批次 `~/.prd-cache/<ID>/plan.md`

把清单行归并成步骤，每步写：覆盖的清单行、要改/新建的文件、依赖哪些步骤。按依赖分批，每批标明是否派子 agent 及理由：

- **批次 0（主会话串行）**：先定下所有步骤都要用的契约，包括类型/schema、service 接口、路由与路径常量、i18n 文件和 key 骨架、共享组件的 props。只有后面还要派并行子 agent 时，批次 0 写完先把共享 query/类型接进一个仓内目标组件的最小调用点，再跑一次 check.mjs 锁定契约；串行时直接放到 §6 一起查。不依赖契约的零散步骤和批次 0 同时开工。
- **能否并行看依赖**：两批互不改同一文件、只依赖批次 0 已定的契约、不需要对方的产出，才算可并行；否则排成先后批次。
- **值不值得派看工作量**：可并行的批次里，只派工作量明显大于子 agent 重建上下文成本的（如另一个工程、独立页面）；零散小改动主会话顺手写。没有值得派的就全程串行。
- **值得派的有 ≥2 批时**，主会话只做批次 0、合并和验证，不写大段 UI；只有 1 批时派它出去，主会话写主线。
- **派子 agent 时**：每步一个，给它清单行原文、可写文件清单（越界只读）、契约文件路径、§5 编码规则；不跑 git（删文件用 `rm`）、不跑全量检查，返回改了哪些文件和未决问题。共享组件写明只允许做什么（如「只加可选 prop」）。这一批都返回后**逐个看 diff 合并**（报告可能与改动不一致），再开下一批。
- §6 静态检查通过后，**冷读子 agent 与浏览器子 agent 同时派出**（浏览器后台先派，再前台派冷读；都不改业务代码，结果先写入 `~/.prd-cache/<ID>/coldread-N.md`、`browser-roundN.md` 再返回，中断后读文件续），**两者都返回后才改代码**（先回来的可先列修复方案，改代码会打断 spec）；**结果回来前不进 §8/§9、不结束或交回任务**。

`~/.prd-cache/<ID>/run-log.md` 记每批起止时间、返工原因和意外。

## 4. Worktree

```bash
node $S/worktree.mjs <ID> [--fix]              # → ~/github/<ID>，feature/<ID> 基于 origin/online，自动装依赖
```

已存在就复用；远端已有同名分支时脚本拒绝创建，改用 `--branch <名字>` 或问用户。之后改动都在该路径内。

**禁止在 fameex-web 用 `git stash`**：所有 worktree 共用 stash 栈。对比改动前后用 `git show HEAD:<file>` 或临时 worktree。

需浏览器验证时，建完 worktree 就对涉及站点跑 `browser.mjs check`，失效立刻请用户 `login`、编码照常进行（`references/browser.md`）。

## 5. 编码

- 按 §3.5 的批次推进：批次 0 主会话自己写；后续批次按 §3.5 判定值得派的才派子 agent，其余主会话串行写，派出时主会话负责合并和对齐契约。
- 遵守全局规则和仓库 `AGENTS.md`/`CLAUDE.md`、按主题命中的 `.cursor/rules/*.mdc`、`coding-quality` skill。
- 按清单逐行实现，实现完一行就填上真实落点。
- 文案按 PRD 逐字写入，语言文件范围按仓库规则。含 `&`、`/`、`<` 的文案能直接写就不走插值（会被转义成 `&amp;`）。
- 接口未就绪时按已知契约写好代码，清单标「待联调」，并**自行决定**加最小 MSW mock 把 UI/UX 写全：只为本需求新增/变更的接口写 handler 和 fixture（`src/mocks/<功能>/`，仅 `NEXT_PUBLIC_ENABLE_MSW=true` 生效，业务代码无 mock 分支）。未接入的 app 按 `references/fameex.md` 单独提交补齐（legacy 不接）；接口上 dev 就删 handler，基建保留。边缘数据态写在浏览器 spec 的 mocks 里。
- PRD 要求埋点时，事件参数（步骤序号、来源页等）由纯函数算出并单测断言取值（浏览器验不到埋点）。
- 写操作（绑定/解绑/提交/删除/状态上报）成功后，要让依赖该数据的服务端状态刷新（React Query `invalidateQueries` 用户资料、列表等），不能只关弹窗、弹提示。

## 6. 检查（只查改动）

```bash
cd ~/github/<ID> && node $S/check.mjs [--base <BASE>]   # biome + tsc（只报改动行）+ code-rules（豁免写 `// code-rules-ignore <ID>: <理由>`）；legacy JS/.vue 做语法检查；改动的测试文件跑 vitest
```

手动格式化（`biome check --write`）只传本次改动的文件，不传目录。`not-covered`（如 legacy `.vue` 模板）不算通过，交付说明如实写出。

**浏览器验证（改动涉及可见 UI 时必做）交给 1 个浏览器子 agent**：给它清单、`media-notes.md`、`git diff <BASE>`、`references/browser.md`，要它按清单每个页面/入口写 spec 跑（接口没好就在 spec 里 mock），返回问题列表、spec 路径和 not-covered 项，不改业务代码；截图只看视觉相关步骤（每个页面状态 1 张、失败步骤必看），文案/显隐用 `expectText` 等断言判。§8 修完后用 SendMessage 让**同一个**子 agent 重跑受影响的 spec，只看 report 的通过/失败与 pageerror。跑不了的写 `not-covered: <原因>`，不假装通过。

## 7. 独立冷读（必须用子 agent，不能自查）

开一个**全新上下文**的子 agent（Claude 用 Agent 工具；Codex 用新会话或子代理）。只给它下面这段话，不要附带你的推理过程：

`<BASE>` 默认取 `git merge-base HEAD origin/online` 的结果；回放时用指定的 base commit。冷读前先 `git -C ~/github/<ID> add -N .`，否则 diff 里看不到新建的文件。

> 你是需求验收员。PRD 在 `<prd.md 路径>`（内嵌表格已展开），图片在 `<media 路径>`，额外输入在 `<inputs 路径，没有就删掉这句>`，代码改动用 `git -C ~/github/<ID> diff <BASE>` 查看。语言文件范围以仓库 `AGENTS.md` 为准。
> 1. 独立通读 PRD 和每张图，列出所有前端可见行为：页面、入口、文案、校验、状态、权限、埋点、多语言。不要看任何现成清单。
> 2. 对每一条，在 diff 中找到实现它的具体位置（文件:行）。找不到就标 **MISSING**。如果交付方声称「本仓无此页面」，自己在全仓搜一遍（包括 `legacy-admin` 等 Vue2 旧工程），找到了就标 **MISSING** 并给出路径。
> 2b. 有接口契约（inputs/）时逐个核对：PRD 要求的展示与提交，读写的是不是契约写明的那个字段（如契约注明「译文」的字段），本需求新增的请求字段是否每条提交路径都带上；不对标 **MISMATCH**，漏带标 **MISSING**。
> 3. 对每个被改的常量、正则、枚举、组件、文案 key，在仓内全局搜索其他拷贝和调用入口（包括写死的字面量副本；i18n key 要搜扁平和嵌套两种写法），把没跟着改的标 **SIBLING-MISSED**。
> 4. 标出与 PRD 原文不一致的文案、校验、显隐条件和行为（**MISMATCH**）；为某一类对象做的改动波及或泛化到其他类型/板块/渠道，也标 **MISMATCH**（范围外）。
> 5. 如果改动收紧了校验规则，检查有没有误套到「验证已有值」的入口（登录、校验旧密码等），有就标 **MISMATCH**。
> 6. 检查页面规则提示/勾选状态是否与提交校验一致（有没有「全部显示通过但提交被拒」的输入），以及旧提示写明的条件有没有在新提示里丢掉，不一致标 **MISMATCH**。
> 7. 检查每个写操作成功后，依赖该数据的列表/资料是否会刷新，不刷新标 **MISSING**。
> 被 lint-staged/biome 强制要求的存量最小修复（如去掉 `any`、格式化）不算越界，不用报。
> 只输出问题列表，每条附 PRD 原句和证据。不要修改代码。
> 后端直出的字段/口径不要求前端改写或推算；前端用兄弟字段做算术反推的，标 **MISMATCH**。
> `<额外约束：范围限定、回放的公平性约束等，没有就删掉这一行>`

## 8. 修复（最多 2 轮）

逐条处理 MISSING/SIBLING-MISSED/MISMATCH：修复，或给出理由（后端原因、PRD 明确不做）。**PRD 正文明确要求的改动，不因冷读的顾虑撤回或降级为 blocker**：实现保留，顾虑列待确认；确实缺数据且 schema 无现成字段才列 blocker。**同因** = 同一业务对象/字段在其他页面、入口、拷贝里的呈现，必须一起改；**范围外** = 本需求没涉及的其他对象/渠道/类型的已有行为被连带改变，或新功能被泛化到它们身上（如只为 TradFi 做的 Tab 变成遍历全部板块），默认收窄（PRD 要求统一才保留）。同因扩展找不到口径依据时不做，列待确认。修完重跑 §6。**第 1 轮修过 MISSING/SIBLING-MISSED，或修复改了 ≥3 个业务文件（不含测试）**，才冷读第 2 轮，否则主会话逐条核对并在 run-log 记一笔。第 2 轮提示附第 1 轮问题与处理结论，只复核修复、新增 diff 与「保留」理由。第 2 轮的问题主会话直接修（运行时问题让浏览器子 agent 重跑），仍有问题交给用户。

## 9. 提交

```bash
cd ~/github/<ID> && git --literal-pathspecs add -- <本次改动的具体文件...> && git commit -m "feat(<ID>): <一句话>"   # 文件多时用 --pathspec-from-file=<file>；--literal-pathspecs 防 [lang]、(group) 被当 glob
```

- 只 `git add` 具体文件，不用 `git add -A`。不 push。
- 被 hook 拦下就修代码，不用 `--no-verify`。
- 沙箱里 `.git` 只读、提交失败时（Codex CLI 常见）：`git bundle create /tmp/<ID>.bundle <base>..HEAD` 打包提交（可先在临时 `GIT_DIR` 里提交），并在交付说明里写明 SHA 和 bundle 路径，由用户 fetch 回来。

## 10. 交付说明（给用户，≤15 行）
